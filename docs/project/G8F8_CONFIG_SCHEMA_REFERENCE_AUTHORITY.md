## Generated Header Role

`.pio/build/glyph_mk6/nanopb/generated-src/config.pb.h` was present locally and begins with an automatic-generation notice. It can be cited to understand generated enum names, struct field names, counts, and nanopb output in the current local build. It should not be edited. If it conflicts with the active proto/options source, regenerate through the build system rather than hand-editing.

## Runtime Defaults Role

Repo-tracked defaults such as `HAL/pico/include/config_defaults.hpp` and `config/glyph/common/include/glyph_overrides.hpp` are evidence of compiled runtime default config contents. They are not evidence that a host configurator UX can author those fields, and they are not proof of an export/import file format.

## Rules For Future Senscope Adapter Citations

1. Cite the active proto dependency path and pinned dependency source when discussing wire/config schema.
2. Cite generated `.pio` headers only for local generated layout evidence, never as hand-edit authority.
3. Cite repo defaults only for compiled runtime default behavior.
4. Mark copied docs/reference files as `REFERENCE_ONLY` unless a build/include path proves they are active.
5. Preserve dependency scope: Glyph envs use the Glyph override in `config/glyph/env.ini`; do not silently promote base env dependency claims to Glyph env claims.
6. Do not infer host UX or export format support from schema availability alone.

## Conclusion

For the current local `glyph_mk6` build, the strongest schema authority is the active `HayBox-proto/config.proto` dependency path selected by PlatformIO plus the Glyph env dependency override. Generated `.pio` headers are useful local evidence but not edit targets. Repo-tracked defaults are runtime default evidence, not host UX/export evidence.
