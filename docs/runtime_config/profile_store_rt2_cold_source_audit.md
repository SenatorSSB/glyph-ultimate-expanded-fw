## Scratch authority and conflicts

Official RP2040 datasheet §4.7.4, p545 (https://datasheets.raspberrypi.com/rp2040/rp2040-datasheet.pdf#page=546) specifies eight scratch words survive soft reset and RUN/DVDD reset clears them. §2.8.1.1 p130 reserves scratch4–7 for ROM jump routing; ROM clears4 before jump. REASON p548 is zero on hardware reset, TIMER1/FORCE2. Local pinned generated watchdog register definitions lines84–145 agree. SDK1.5.1 watchdog.c77–96 writes4=0 for watchdog_reboot(0,0,10), leaves0–3 untouched;39–40 selects reset of everything except oscillators. RP2040Support.h278–282 invokes this and never returns. Project HAL/pico/src/reboot.cpp delegates to rp2040.reboot().

Project scratch0/1 belong backend/mode selection and menu overrides: DefaultConfigMenu.cpp178/298–301/348–351; OopsieMenu.cpp44/56; RemapMenu.cpp27–29; config.cpp132–133/146–149/160–162; backend_init.cpp50–65/102–122/278–288. scratch2 exact mode tag0x4d445354 is written only after checked durable Config publication; ModeSelectionTransaction.hpp18–20 clears0/1/2 only for that exacttag. scratch3 is RecoveryStartupDiagnostics v4–v10 namespaces 0x5254/56/57/58/59/5a/5b/5c/5d; TakePrevious clears3 and core1 may later update3. It is unsuitable for recovery intent. SDK/ROM scratch4–7 MUST remain untouched by candidate marker helper. Official ROM bootrom_main.c194–202 reset_usb_boot uses0/1 as USB boot parameters and4–7 via SDK routing, not2. Those MB1 bootloader semantics remain distinct.

Recommendation: use scratch2 with a distinct exacttag, for example0x43525432 (CRT2). Boot A arm only if0/1/2 are allzero, explicit RT2&&!MB1, ordinary boot and no consumed cold RAM flag. Do not erase/repair a conflicting mode marker. At original early TinyUSB init entry recognize exacttag, clear2 first, then validate reason TIMER==1 and0/1zero; invalid exacttag is consumed but refused as recovery authorization. Leave every othertag untouched. scratch3 and4–7 are never used by intent logic. Power/RUN removes intent; after early consumption any later reset cannot replay it. Before consumption an unrelated watchdog TIMER reset cannot be distinguished from the intended TIMER reset; report that inherent bounded residual, not a promise of arbitrary-reset atomicity. Unique exacttag is collision avoidance, not authentication against arbitrary injected matching bits.

## Boot invariants and attachment order

Boot A: original ordinary USB first; sample matrix; MB1 wins RT2; RT2&&!MB1 before display/storage/backend constructs arms single ephemeral marker and calls existing watchdog reboot once. No ProfileStore Begin, Config load/save or recovery service construction merely to reboot. Conflict publishes refusal, no fallback/cleanup/retry.

Boot B earlyoverride: consume marker and RAM-flag before descriptors, USB mutex/queue/IRQ allocation or attachment; defer ordinary begin. App setup first tests RAM flag, before matrix/display/normal Config/store/backend path; do not require or inspect RT2/MB1 again. Run existing initialize_recovery, prepare CDC composition, construct ConfiguratorBackend, install SetRecoveryState, finalize identity, then call unchanged pinned TinyUSB_Port_InitDevice once. Descriptor helper may run before storage provided identity is finalized later and no clear occurs afterward. Existing Serial.begin is idempotent for valid CDC but prefer no redundant call.

Port.cpp98–113 creates __usb_mutex, calls tud_init, claims task IRQ and registers trigger. usbd.c407–450 creates USBD mutex+queue once, initializes all compiled class drivers, then dcd_init/int_enable. DCD393–427 resets hardware once, registers DCDhandler, creates EP0, resets noncontrol, enables USB and connects via pullup; dcd_connect470–473 sets pullup. Thus pullup occurs INSIDE port call before port task IRQ registration completes, but AFTER application descriptors/backend/read-only state. Do not falsely claim pullup is literally last instruction or IRQ registration. Exactly one cold init yields one portmutex, USBDmutex, queue criticalsection, task claim, DCDhandler and shared trigger. Compiled XInput/class init may exist while recovery descriptor composition must contain CDC only; descriptor absence does not imply compiled driver absence.

Failure: consume attempt before any preparation/start; preparation failure refuses without USB init, no ordinary fallback. Start is one-shot consumed BEFORE invoking void pinned port. Bounded returned failure publishes RecoveryTransportFailure; no start retry/reboot/detach-reset. Pinned queue/IRQ asserts/panics may never return, so publication after every internal panic cannot be promised. All failure paths retain inspection-only store policy and cleared intent. initialize_recovery.hpp18–31 uses SetValidator, IsAvailable, LoadConfigChecked, BeginRecovery; no normal Begin/migration/selection or durable write.
