## Findings

- `get_usb_backend_config_default` copies the one-based selected backend only for indices greater than zero and no greater than the configured backend count. The exhaustive initialized-output matrix covered all 256 stored `uint8_t` values at each count from zero through fifteen: 120 in-range copies and 3,976 out-of-range outputs left at the harness sentinel. It never reads the production caller's uninitialized local.
- Source-level invalid-index path: `initialize_backends` declares `CommunicationBackendConfig usb_backend_config;` without initialization, calls the getter, then passes `usb_backend_config.backend_id` to `init_primary_backend` before detection. For index zero or greater than the configured count, the getter does not assign the output, so this path reaches the initializer with an indeterminate `backend_id`. This is a concrete source finding; the host harness deliberately uses an initialized sentinel and cannot establish a deterministic value, runtime outcome, or physical symptom for the production path. This work order authorizes characterization only, so the finding requires a separately curated repair or exact nonblocking disposition before any policy or source change.
- The selected schema declares tag 7 as `uint32`; accepted generated storage is `uint8_t`. The exact GP-PROV-014 record describes an observed Nanopb 0.4.9.2 package and exact generated/schema closure; it does not pin future package resolution.
- Decoder rows: omitted tag 7 succeeds with zero; repeated tag 7 succeeds with the last value; 256 is rejected; an invalid trailing varint rejects while retaining the earlier decoded tag-7 value 2 and one backend; wrong-wire-type and overlong-varint inputs reject. Sixteen backend entries are rejected, with the generated count field left at 16 in the rejected partial object. These are decoder observations only; they do not establish how the Persistence `LoadConfig` path uses rejected partial output, saves it, or continues initialization.
- In injected initialized host configurations, XInput, DInput, Switch, and Configurator detection all first initialize the configured USB default and then select that same USB config. GC detection first initializes the USB default, then selects the matching GC config. RF3/DInput and RF2/Switch held-button selections bypass detection and the preliminary USB initializer. A separate source-bound DInput case passes the Keyboard `GameModeConfig` through the existing DInput applicability branch. A watchdog override bypasses held-button selection; the fixture's sample sets mode 2 and records one save. Unspecified detection returns zero after the two recorded initializer calls.
