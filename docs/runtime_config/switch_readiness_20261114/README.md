# Switch USB readiness review candidate

Firmware source `0b9ef3afd1834ac7832871bca0651b67147840a2` has direct parent `84556d904f067bda5a101e6297689239ecd04aae`. Build the source commit when reproducing the candidate. The evidence commit adds files after the source identity was embedded. Review only.

## What can stall

On Mk6, normal Arduino RP2040 main calls loop() on core 0. The common Glyph config selects the mode, services pending profile selection, and dispatches the configured backends sequentially. backend_init registers the Switch descriptor and constructs NintendoSwitchBackend. SendReport runs SLOW and MEDIUM scans before its readiness wait. In the parent, permanent false prevents the FAST scan, UpdateOutputs, subsequent backends, runtime identity polling and the next core 0 iteration. The Mk6 matrix is the FAST source. Core 1 independently calls IntegratedDisplay::SendReport. Its HandleControls reads the shared InputState without rescanning the matrix. Redraws can continue while controls appear frozen.

The owner saw a freeze after selecting Switch on Mac, and subsequently verified restored XInput operation and storage preservation. No capture measured readiness or the program counter at that freeze. The host negative control establishes a causal chain for an injected false endpoint. Stage F attribution and receiver compatibility remain open.

## USB and scheduling

The Mk6 configuration pins arduino-pico 3.6.3 (32e74d0), including Adafruit TinyUSB 2.3.0 (e291865). Adafruit_USBD_HID::ready calls tud_hid_n_ready. The pinned hid_device.c checks tud_ready (mounted and unsuspended), a nonzero IN endpoint, and absence of endpoint busy. An unconfigured/disconnected or suspended host can keep this false. A configured receiver can leave an outstanding IN transfer busy by ceasing polling. Simply connecting a Mac does not establish any one of these states. The RP2040 USB interrupt schedules a software IRQ that runs tud_task when its lock is available. The original tight_loop_contents supplies no USB work or deadline, though interrupts can still progress.

TUCompositeHID requests a 1 ms poll interval. The new timer grants one such interval starting after MEDIUM, preserving wait-then-FAST sampling on prompt hosts. XInput's separate 50 ms timeout illustrates the starvation issue but would consume 50 Switch poll intervals. DInput's similar wait remains a separate investigation. A free-running output update on each busy check could sample additional transitions in stateful input modes. The bounded design permits ongoing scans during longer stalls, without a new scheduling subsystem.

When continually unready, the first deadline check at or after 1000 microseconds exits the polling loop. This bounds the requested wait, subject to timer/check overhead and interrupt scheduling. It is not a bound on the entire scan, menu latency, or transfer completion. Every case still runs FAST and UpdateOutputs. A timeout skips that report, and a later turn samples current input. When ready, the existing packing and transformations run, with one last readiness check immediately before submission. No retries, queue, replay, or success bookkeeping were added. The USB stack separately claims the endpoint and attempts transfer. A disconnect after the final sample is inherently possible and a local submission is not proof of host receipt.

## Independent review and results

The optional keyboard transport is DInput-gated. Four deliberate defects were each rejected: skipping FAST on timeout, dropping the final readiness check, swapping Y/B, and doubling the wait.
