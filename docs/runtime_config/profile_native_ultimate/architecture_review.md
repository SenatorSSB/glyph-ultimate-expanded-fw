## Concrete issues sent directly to designer

1. **Sparse/reordered user roles are a real admitted legacy case.** `config_validation.cpp:140–175` admits up to22 distinct role IDs1..32 and requires lower-ID dependencies; it does not require dense IDs or serialized topological order. The initial witness appends roles in serialized order but translates role references by `intrinsic + oldID`, so it misbinds sparse or reordered IDs. Example: a sole old role32 with a table rule referencing token96 is admissible; the witness appends new role31 but emits reference62. Acceptance: explicit old-ID→new-ID map, topological conversion independent of persisted order, and sparse/reordered fixtures exercising role/rule/effect gates.

2. **The initial ordinary witness is not a general V3 converter.** It copies fixture phase/target/coordinates but hardcodes activation/source/gates and omits arbitrary gate inversion/suppression/D-pad value variations. `UltimateProfileEvaluator::ValidEffectShape` and `config_validation.cpp:176–199` accept these variations. `Ultimate.cpp:715–849` applies Stage-C outer guards, source transformation, mode table choice, phase precedence and digital-mask-before-trigger semantics. Acceptance: a complete algorithm for every admitted V1–V3 representation, a finite bound accounting for added generic outer guards plus independent user graph, and tests that vary every legal gate/source/coordinate/value/suppression family. It is valid to defer production differential execution to M2–M5, but not to describe this fixture shape as already proving arbitrary parity.

3. **V2 and V3 routing have different observation domains.** `RouteLogicalInputs` applies only to V3. In V2, digital/analogue intrinsic roles consume post-SOCD physical/logical inputs directly while table role/rule selection resolves V2 routes internally. V3 intrinsic output resolution consumes routed inputs, while user roles/effect gates resolve once from the original processed snapshot. Acceptance: converter separately maps those meanings; no global route composition or second routing pass. Nonidentity route fixtures must distinguish the versions.

4. **Callback ownership must cover every descriptor consumer.** `ProfileStoreRequestIdentity` re-encodes the decoded request synchronously with token zero; Configurator later reuses its frame for the response. Record ReadProfile/WriteProfile use separate static wire buffers. No native callback may point into an input frame overwritten during response or into mutable record scratch exposed as active program. `RuntimeProfileDigest.hpp` currently depends on generated `UltimateProfile_size`; FT_CALLBACK may remove that and dependent generated size macros. Acceptance: descriptor generation evidence, explicit finite replacement bounds, repeatable size/encode callbacks, duplicate native-field rejection, and immutable owned body through request hashing/transaction/readback/response hashing. Test callback alias mutation and encode-size versus actual-byte mismatches.

5. **Unconfigured Config callbacks can silently discard tag8.** Current Persistence LoadConfigChecked/ReadLegacyProfile and Configurator SET_CONFIG initialize profiles then call `pb_decode` without native callbacks. Empty callback handlers normally skip bytes. Acceptance: explicit rejecting/presence-tracking handlers or bounded preflight at all Config/profile entrypoints, so schema1+native-body mixed payloads cannot be silently accepted as legacy; schema5 embedded in Config must reject. Config copies must not retain live native callback pointers. Native payloads remain store-only.

6. **Nunchuk tail semantics need explicit preservation.** `Ultimate.cpp` final two overrides observe original processed `inputs.nunchuk_c/connected/x/y`, not Stage-C routed button slots. D-pad nunchuk routes and analogue override order also differ from ordinary intrinsic slots. Acceptance: unchanged source-backed tail with native unavailable bypass, or a narrow generic adapter with exact differential proof; no physical Nunchuk PASS or behavioral redesign claim.
