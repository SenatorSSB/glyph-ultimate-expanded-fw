## Smallest source-supported alternate proposal

This is a bounded **proposed scope**, still subject to separate explicit owner/Curator authority and exact final review/build/disassembly. No SDK cache patch, archive-member replacement, symbol surgery, replacement CRT or dependency rebuild is proposed.

**Core0:** one repository-owned stackless assembly `__wrap_main` entered through crt0's actual undefined main reference. It initializes only its own inactive usable stack interval, preserves ABI/LR/PRIMASK, then tail-calls external `__real_main`. An eventual `-Wl,--wrap=main` is plausible because the inspected crt0 member lists main undefined. It must be proved in final ELF that platform_entry reaches the wrapper and the wrapper reaches original Arduino main exactly once. If not, stop; do not accept a plausible flag as proof. Data/BSS/runtime_init/constructors have already executed. Paint covers subsequent Arduino main/framework/application activity only; earlier peaks remain UNKNOWN.

**Core1:** wrap **external `multicore_launch_core1`**, not main1. A small repository-owned core0 wrapper verifies this is the expected single initial launch with the actual Arduino main1 entry, then calls the original default launcher with a repository-owned stackless **core1 entry adapter** instead. The existing SDK default launcher still chooses the same reserved2048-byte stack and performs its existing trampoline/guard/IRQ setup. When the adapter runs on core1, it paints only core1's own inactive usable interval, preserving active launcher/wrapper frames, then tail-calls original main1. The adapter's reference to actual main1 is intentionally a normal external reference, without `--wrap=main1`. There is no new core reset, start/stop, alternative stack, cross-core painting, ROM-stack assumption, FIFO protocol, core1_separate_stack enablement or host-controlled entry pointer.

Prefer an immutable expected main1 target rather than a writable general entry dispatcher. Wrapper behavior for an unexpected target/relaunch/separate-stack/FreeRTOS configuration must preserve existing launch behavior without instrumentation and mark the observation unavailable; do not redirect arbitrary entries. Any need to support those modes is excluded from this narrow order. Final review must establish actual `core1_separate_stack=false`, non-FreeRTOS startup, single initial launch, symbol binding/calling convention, cross-core publication safety if a validity flag is shared, and no compiler inline/bypass. A bypass/unverified path means INVALID/NOT_MEASURED, not a zero stack/timing value.

The initial coverage remains core1 adapter-entry onward; ROM, trampoline and core1_wrapper/irq_init_priorities earlier transient peaks remain UNKNOWN. No painting before SDK launch on core0, because ROM stack ownership is not established. The adapter starts after potential stack-guard installation: original guard exclusion is mandatory. Do not read or paint the protected bottom32-byte region. Actual guard state/layout must still be verified from the final artifact, not assumed enabled or disabled.

The original exact path allowlist can contain these replacements in the already proposed `NativeTargetMetricsEntry.S`, `NativeTargetMetrics.cpp` and `native_target_metrics.py`; amend link options to the two external boundaries above. No extra backend/dependency/startup-source path is needed for this alternate. All timer, fixed-read-only XInput response, same-tested-source,512-byte diagnostic subcap, existing total RAM/stack limits, independent review, build/custody and concrete device-packet gates from the original proposal remain unchanged. No current16/72 identity bytes gain new meanings.
