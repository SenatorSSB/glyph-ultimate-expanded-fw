## Decision in one paragraph

Recommend a separate explicit owner/Curator authorization for one small, retained-in-candidate diagnostic extension: SDK hardware-timer observations around native execution and boot activation, per-core reserved-stack write-watermark observations, and one fixed, read-only diagnostic response in the already available XInput CDC session. Keep that instrumentation in the exact source/artifact that receives the chapter's hardware acceptance. This is the narrowest defensible route given the owner's available XInput/Switch/GameCube routes and absence of SWD/probe/external timing equipment. Existing identity/status/read interfaces cannot produce these observations. The new exception must be explicit because frozen architecture §1 prohibits a new timing facility/transport command and implementation_contract excludes transport commands. Authorizing this proposal would not approve a device packet or waive any resource/hardware/completion gate.

The result is **elapsed target microseconds including any preempting work, and observed stack writes over specified post-initialization windows**. It is not CPU-exclusive cycles, an absolute worst-case execution-time proof, exact minimum SP history, or a proof that no stack overflow can occur. If the completion requirement demands any of those stronger facts, this proposal alone cannot satisfy it; that requirement remains unresolved.

## Proposed measurement semantics

1. Native frame interval: two time_us_32 reads bracketing ControllerMode::UpdateOutputs only for the active NativeAbi1 mode. This includes existing remap/SOCD/context and native evaluation/neutral refusal. No input scans, USB readiness waits, backend serialization, stack scans, metric formatting or serial writes in this interval. Do not time only the most convenient inner evaluator and label it complete polling cost. Existing mode/source interfaces must select native mode without adding a second input evaluation. NativeUnavailable is separately flagged/counted, never folded into valid native maxima. If final call ownership prevents this exact bracket, stop for a reviewed precise boundary instead of renaming another number.
2. Boot activation interval: bracket the single selected native boot path from immediately before Activate through SetConfig and publication to backend at the existing mode-selection call site. Include actual record read/validation/preparation/copy/bind and context match; count/flag recovered previous or failure separately. Do not invoke Activate again merely to measure. This is selected-profile activation elapsed time, not power-on-to-first-report. Optionally record setup-entry→Normal publication as separately named application-setup elapsed time from the same timer; never claim it covers ROM/runtime initialization.
3. Timer values are raw unsigned modular deltas, min/max/count plus saturating64-bit sum; no floating point/histogram/dynamic arrays. Intervals must finish within one32-bit wrap; a session with uncertain stall/wrap is invalid, not an enormous valid sample. Keep counts and overflow/saturation validity flags. Record source clock/SDK timer assumption and observed run duration. Leave IRQs normally enabled during timing: preemption/cache/flash/bus stalls remain included. This is useful service cost under the tested workload, not isolated core CPU cost. No inferred cycle conversion or subtraction of host latency.
4. Record a small, fixed automatic boot calibration of adjacent timer reads with identical accumulation scaffolding; report the distribution alongside raw intervals. Do not silently subtract its min/mean from maxima: measurement overhead and quantization vary. A zero-microsecond sample means below resolution/quantized, not zero work. Inspect final disassembly for inlining, optimizer motion and real loads around the call. Use compiler barriers where necessary; retain exact flags. Runtime-derived clock information must never change the clock.
5. Metrics lifetime is one boot; counters monotonically accumulate, saturate honestly and are never reset/started/stopped by a host command. No replaying profiles, synthetic polling, repeated preparation or host-selected memory location. The approved device packet defines finite coverage and run duration. No assertion of absolute worst case based on sample maxima.

## Safe stack observation boundary

Use fixed linker symbol bounds and per-core ownership, not malloc, a larger stack, another stack, or a scan from the other core.

Propose repository-owned **stackless assembly entry wrappers** for runtime_init (core0, after BSS/data initialization but before runtime_init) and main1 (core1, before registerCore/setup1). Link wrapping is a proposed implementation technique, not a verified present hook: exact linked disassembly/relocations must prove every relevant entry goes through it, preserves ABI and tail-calls the real entry. GNU wrapping can fail to intercept internally resolved references. If either wrapper does not intercept on this exact framework build, this bounded order stops; it does not authorize patching downloaded SDK/Arduino files, replacing crt0, copying the framework, or expanding linker scripts. Such a fallback needs a separately reviewed scope. No hidden dependency cache mutation.

At each core's own wrapper, before any push/call, capture entry SP and prior PRIMASK in registers, mask configurable IRQs locally, validate SP/alignment/bounds against that core's two linker symbols, and fill only the aligned inactive interval `[UsableBottom, entrySP)` with a fixed32-bit pattern. Preserve all registers required by the wrapper ABI and caller/LR without placing them in the painted interval; keep original stack contents `[entrySP,Top)` untouched and conservatively count that interval as used. Restore the exact prior interrupt state before tail-calling the original entry. No C helper, library call, constructor, assert, printf, global-object access or dynamic initialization in the painting loop. A static POD result written after BSS clear may record bounds/initial SP; it cannot rely on C++ initialization. Count initialization cost as diagnostic overhead; it is outside the native activation timer.

This avoids painting live C frames and avoids touching core1's possible ROM-owned stack from core0. main1's existing wrapper/launcher frames above entrySP remain intact. **Coverage is explicit:** core0 watermark begins at its pre-runtime hook, excluding ROM/reset/data-copy/prehook use; core1 begins at main1, excluding ROM/trampoline/core1_wrapper/irq_init_priorities earlier peaks. Fill discards earlier write history, so no claim of full power-on startup peak. Main1's active caller bytes are conservatively included, but that does not prove their earlier deepest transient stack use. NMI/fault behavior is not controlled by PRIMASK and is not certified here. Keep prehook gaps UNKNOWN and combine compiler evidence where available.

Account for SDK stack guards before any paint or read: `pico_runtime/runtime.c:42–64` configures an inaccessible32-byte MPU subregion at the rounded-up stack bottom when PICO_USE_STACK_GUARDS is compiled true; both runtime_init and core1_wrapper may install it. Final preprocessor/disassembly must establish the actual setting. Conservatively set UsableBottom=Bottom+32 for these aligned reserves, never touch `[Bottom,UsableBottom)`, and include those32 bytes as reserved/guard overhead, not usable capacity. Do not disable or move a guard. On any other actual guard layout, stop/review the bound rather than probe inaccessible memory.

After initialization, NEVER repaint. Each core scans only its own usable reserved span from UsableBottom upward for first changed word, retaining a monotonic lowest-changed address and the conservative entrySP upper-use region. Use short fixed chunks (at most16 aligned words per loop pass) with locally saved/restored IRQ state for each read chunk; do not hold IRQs off for an entire2048-byte scan. No spin waiting, cross-core stop, FIFO lockout or pause-the-other-core request added. A complete scan requires at most32 chunks per core. Publish only completed scan generations through per-core fixed POD mailboxes with release/acquire ordering or a reviewed SDK equivalent; no64-bit torn snapshots or undefined cross-core data races. Host response may return last complete generation with age/status rather than waiting. If pending, say PENDING.

Scanning/transport/core1 mailbox code consumes real stack and time; its frames/any IRQs contribute to the observed watermark. Measure/report scan service elapsed maximum separately and inspect static frames. Running it after outputs does not make the overhead disappear: it may change the next poll/IRQ timing and GameCube deadlines; full functional/latency regression still applies. No whole-stack scan inside the timed frame or activation call. If16-word chunks are not acceptably bounded for the real timing route, stop/review rather than disable IRQs longer or quietly omit the cost.

A paint watermark observes writes, not every SP excursion: compiler-reserved untouched slots or values coincidentally equal to the paint can hide depth. Report `observed_written_bytes` and sampled-SP information separately. A changed first usable word or SP outside usable reserve is a failure/invalid observation; absence is not overflow-proof. No absolute safety margin from watermark alone; .su/callgraph/IRQ assumptions remain necessary. Dedicated fixed firmware test fixtures may deliberately consume bounded stack to validate detection, but no host-supplied depth/address, no recursion/overflow stimulus on the owner's controller.

## Additional stack-budget classification requested during preparation

The two physical scratch MEMORY banks are4096 bytes each (`lib/memmap_default.ld:24–29`). That does not enlarge the reserved stacks: their lower bounds are computed from the2048-byte .stack/.stack1 dummy section sizes (:248–266), and the final symbols supplied by the writer match the baseline2048-byte reservations. Lower bank space can host .scratch_x/.scratch_y sections (:196–211); it is not blanket stack authority. `__StackLimit=0x20040000` denotes the main-RAM heap ceiling, not a4096-byte stack declaration. Even if an unguarded descending SP can physically reach spare lower bank addresses, that is an excursion beyond the frozen stack budget, not evidence of an authorized4KiB stack. If guards are compiled in, they additionally prohibit a32-byte bottom subregion (:42–64 runtime.c), reducing usable reserve rather than expanding it. Current guard-enabled status remains UNKNOWN until exact built preprocessor/disassembly proof. No source-backed claim of a safe extra2KiB exists here.

The writer-reported Read/Create enumerated-frame inventory2784 bytes is **not** independently established as a feasible simultaneously live call chain. Compare feasible paths, actual O3 inlining/tail calls/branches, reused storage, baseline paths, ABI and IRQ overlap before classifying it as an overflow. Preserve that inventory and any concrete over-budget feasible chain as evidence, not a fabricated actual peak. Likewise frozen native validation256 refers to the new native validation workspace/local layout, not a cap on every existing nested hash/runtime call: report the actual composed chain separately. Parent-supplied current structure144+Token16+Prepare24=184 and hash-branch full-chain432 are distinct scopes, not a256-byte composed-chain PASS. This proposal does not independently reproduce those numbers. Any demonstrated feasible total above2048 (or actual usable reserve after guard), including preemption and monitor overhead, is a substantive budget defect requiring bounded redesign or explicit owner resource decision; it cannot be repaired by relabeling scratch-bank capacity or relying on a sample that happened not to fail.
