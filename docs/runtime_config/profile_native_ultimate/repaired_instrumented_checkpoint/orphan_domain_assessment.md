## The conditional invariant and why it is useful

Start with a successfully formatted filesystem containing only root-directory regular files and no pending directory-orphan state. Allow the actual firmware's root-file open/read/write/sync/close, atomic file rename, file removal, metadata split/relocation, mount/unmount, checked I/O errors and power loss during those operations, with LittleFS's own commit/CRC recovery model. Do not silently add arbitrary CRC-valid metadata rewriting, foreign directory creation, or an unproved initial image to this premise.

Within this closed domain, source supports the invariant: no physical child-directory `LFS_TYPE_DIRSTRUCT` is introduced; the orphan-count bits stay zero in gstate/gdisk/gdelta and committed global state. A pending regular-file MOVE is still possible and remains a separate required64-byte allowance.

Evidence:

1. Initialization zeroes gstate/gdisk/gdelta (`lfs.c:3999–4001`). Successful format emits only superblock/name/inline-structure records (`4046–4080`), not DIRSTRUCT. A logical ProfileStore Directory is a regular-file payload, not a physical LittleFS child directory.
2. Every positive `lfs_fs_preporphans(+1)` site is enumerated: mkdir's directory-chain insertion (`2441`), removing a physical directory (`3649`), replacing a physical directory in rename (`3761`), and relocating a directory pair which has a DIRSTRUCT parent (`2275`). The other calls decrement/clear existing orphan count.
3. The relocation parent search (`4400–4421`) matches exactly DIRSTRUCT. With no physical child directories, root and root-continuation metadata pairs cannot satisfy that parent predicate. Root split/expand (`1662–1694`,1907–1998), file creation/truncation/sync and root-segment relocation therefore do not create positive orphan count. Cross-pair file rename uses prepmove (`3774–3799`), whose bit mask preserves orphan-count bits; MOVE cleanup is not directory-orphan creation.
4. Source-owned current config filenames are `config-v2.bin`, `config-v2.prev`, `config.bin`; migration source/temp, v1/v2 logical roots/control, and ID/revision record/temp paths are all regular files at `/`. User profile display names do not become filesystem paths. CollectGarbage removes only matching root regular files and explicitly skips directories (`ProfileStore.cpp:1273–1298`). No production mkdir or lfs_migrate caller was found in HAL/pico/src, src, config or include. Persistence disables autoformat (`Persistence.cpp:120–123`). The historical f7ba and B config/store writers also use flat regular-file paths, not child directories.
5. Store v1→v2 bootstrap, embedded-profile import/migration, control phases, rollback/reconciliation and recovery keep using those same regular-file adapters. They do not invoke LittleFS's optional on-disk v1-filesystem migration, and do not create a directory capability. Mount accumulates valid committed gstate; replay of these file-only commits does not synthesize a new DIRSTRUCT or positive orphan count.

Consequently, for this explicitly closed history `lfs_fs_deorphan` is called (and allocates its176-byte frame) but immediately returns at its `!hasorphans` guard (`4480–4483`). That176 frame is not co-live with its nested orphaningcommit/compaction chain. It must be bounded as its own shallow branch, not added to a compaction peak which has already returned or has not begun. This is a source invariant argument, not absence-of-witness reasoning. It does not exclude forceconsistency's distinct inlined demove→orphaningcommit path, whose64 frame remains live during real compaction.

## What this does not establish

The current ProfileStore Begin/Admit APIs do not prove that a mounted filesystem came from the above closed history. Begin phase2 validates the named control/root contents and incarnation/generation and then returns after reads; it does not reject all unrelated physical directories, inspect global orphan count or authenticate filesystem provenance. Capacity charges actual usage and checks reserve; CollectGarbage explicitly ignores unrelated directory entries. Thus a valid pre-existing physical directory alongside healthy named config/control/root files is not, by itself, rejected by the shown admission rules. A directory occupying a required control/root path can instead cause decode/size/probe failure and recovery: these cases must not be conflated.

A mountable image with pending directory-orphan state plus otherwise healthy required files is structurally different from malformed profile payloads or a missing/corrupt required root. Its provenance is not established merely by Begin returning ready. SDK mkdir/directory replacement could construct such states outside the firmware-owned capability set; **this review does not claim that such a foreign operation is authorized, exposed by the firmware, performed on the device, or a demonstrated source-history witness.** No actual firmware-only transition yielding positive orphan count was found under the invariant premises. Conversely, no universal proof for every mountable, currently accepted pre-existing image follows from those premises.

No concrete physical/host disk witness jointly satisfying accepted Begin, positive orphan count, nested orphaningcommit and compaction is claimed by this finite pass. Adding a synthetic foreign mkdir solely to make a deep callback fire would not settle whether it belongs to the required domain. An unrelated-directory acceptance source observation is not falsely promoted to that stronger witness.
