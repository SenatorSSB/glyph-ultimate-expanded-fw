2. IOUSBHostInterface initWithIOService:options:queue:error:interestHandler: accepts an IOUSBHostInterface service (Interface.h51–60; Object.h27–45). Use optionsNone only, a dedicated serial I/O queue and an error/interest handler. It establishes exclusive ownership and can return nil if the service is missing or its user client already exists. ## Finite cancellation and ownership requirements

SDK Pipe.h213–229 requires completionTimeout=0 for interrupt pipes; zero means no transfer timeout. A synchronous sendIORequest therefore cannot itself provide the required finite observation bound. Use asynchronous submission, at most one pending read, a separate deadline timer on the I/O queue, finite report/submission count and no read resubmission after failure/deadline/cancellation. Serial observation state must not race the interest handler, which Object.h40–43 places on a separate internal queue.

Pipe abortWithOption:error: aborts pending I/O; Definitions.h121–135 says asynchronous returns immediately, synchronous waits for aborted I/O completion. No finite cancellation deadline is specified. A proposed finite observer should request asynchronous abort once at its deadline, stop new submissions and wait only a separately bounded drain grace. If completion does not arrive, mark UNCERTAIN/STOP and retain the entire pipe/interface, buffer, completion block and capture state until process exit. Do not destroy/release pending context or close a FILE still referenced by late callbacks. Detach/retain journals safely before fallible logging. Completion records IOReturn and actual bytesTransferred (Definitions.h16), never status alone; any read error/short/oversize/unknown transfer invalidates qualification and receives no retry. A synchronous abort on the same serial callback queue must not be used as a finite cleanup guarantee.

After a settled completion or proven drained cancel, release the pipe and call interface destroy once before release (Object.h79–84); destroy removes user-client connection/interest registrations and is idempotent. Its contract does not itself promise draining every callback or a finite wait. Normal and exception/timeout/termination/late-callback ownership cases require focused offline mock/sanitizer tests before a future artifact is eligible for review. No such implementation or tests were performed in this feasibility task.
