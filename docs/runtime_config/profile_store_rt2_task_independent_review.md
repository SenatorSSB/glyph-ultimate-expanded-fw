## Scope and identity

The reviewed source and checker changes are the fourteen paths in the inventory: recovery route and core1 loop, USB/task and startup diagnostics, read-only response fields and schema, the task observer checker and fixtures, and the adapted older startup checker and fixture. The inventory's fourteen SHA-256 values were independently rehashed against the worktree and all matched. The worktree is still based on `88ab0029d464175865e1ce3e9a19b462579ffed4`; the new candidate SHA/tree cannot be asserted until commit. The original 88ab RED result and the separate b075 MAGENTA result are preserved without combining boots. B2 chip2/ROM3 with E5 flags zero supports `E5_PHYSICALLY_INAPPLICABLE_ON_TEST_CONTROLLER`; it does not diagnose RT2.

The reviewed source adds observation only. It does not bound `tud_task_ext`, reorder/drop TinyUSB events, change persistence, detach USB, write flash, or operate a controller. The foreground wrapper calls the real `tud_task_ext` once with original arguments and records entry/return on core0 outside exceptions, after the recovery loop arms it. The DCD event hook records raw BUS_RESET and SETUP emissions in USBCTRL IRQ context; a hook invocation can occur even when queue insertion failed. The existing real `usbd_control_reset` wrapper records completion after the real function returns. In the pinned `usbd.c`, `usbd_reset` is its only caller, for both BUS_RESET and UNPLUGGED, and configuration/class resets precede control reset. Consequently the progress marker is **generic RESET/UNPLUGGED processing completion**, not proof that any particular emitted BUS_RESET was consumed.

The independent publisher is source-supported. In the pinned Arduino-Pico `main.cpp`, `main1` calls `setup1` and then repeatedly calls `loop1` even when `setup1` returns early. Recovery is classified as a refused normal boot in `setup1`, so it returns before constructing the RGB/menu/display objects. The recovery branch in `loop1` precedes the other refused-state branch; it reads the observer, writes the existing PIO indicator only on changed valid states, and returns. Core0 hands off the indicator before publishing the boot state. Core1 performs no Configurator, profile-store, TinyUSB or gameplay action on this route. The existing resource sample remains before the recovery branch; it scans core1's initialized watermark and has no USB dependency.

The observer's first-invocation task color remains anchored after the first return; later active/reset counts are separate read-only fields. Atomic 32-bit banks and odd/even publication sequences reject interrupted snapshots without waiting for the writer. The independently retained ARMv6-M assembly probe shows loads/stores and barriers in the DCD path, with no atomic helper call, allocation or lock. The host state probe exercised concurrent reader snapshots and the before-active/after-active/after-clear interrupt windows. A color is a bounded source observation, never a timer-based proof of an infinite hang. The PIO latch is source-supported by the pinned four-instruction program and empty-FIFO behavior, while actual LED visibility remains a hardware question.

## First-task and reset-path audit

Pinned TinyUSB 0.16 `tud_task_ext` drains its bounded queue until `osal_queue_receive` returns empty; under this target's Pico OS mode it has no per-call event cap. Replenishment could therefore keep one foreground invocation active. The queue capacity is sixteen events. Its send result is ignored by the DCD hook, so raw emitted reset counts can exceed accepted queue entries; the observer deliberately avoids claiming queue acceptance. USBCTRL hardware IRQ may keep receiving events while foreground holds Arduino-Pico's USB mutex; its software task IRQ may fail its try-lock separately. The source does not establish an actual physical reset rate, endless drain or overflow cause. SUSPEND/RESUME are filtered before enqueue and again during task handling when `_usbd_dev.connected` is false; hardware IRQ receipt can still occur without task-queue replenishment.

The exact target has CDC, MSC, HID, MIDI and the application XInput driver. HID/MSC resets clear fixed state; XInput reset is a no-op. CDC/MIDI clear fixed interface state and FIFOs. Their `tu_fifo_clear` path can acquire Pico OSAL FIFO mutexes with a wait-forever timeout when non-null. Thus the callbacks contain no USB hardware wait or allocation, but should **not** be called unconditionally nonblocking. Recovery core1 uses no CDC/FIFO operation and the foreground service path releases its stream guard before the USB task; no specific contending holder is established. A single-reset callback stall remains a hypothesis, and the new generic post-control-reset marker distinguishes completed processing from an earlier stall without pretending to locate it inside a class callback.

The exact first-loop path `SendReport → ReadByte → CoordinatedCdcStream::available → fillRx → serviceRx → TinyUSB_Device_Task → tud_task_ext` was checked against the source. Before host connection or input bytes, the CDC FIFO read itself has no wait for a host byte. The potentially open-ended segment is the real task queue drain, or processing inside one dequeued event; neither is declared the cause of 88ab RED. The foreground diagnostic cannot sample again if its first task call fails to return, which is why the core1 observer is material.

Its phase-eight expectation matches the `ReadOnlyInstalled` enum and both frozen/non-frozen startup runs pass. The lead developer's exact worktree PlatformIO build log reports PASS, RAM 187852 bytes and flash 487076 bytes; this is precommit build evidence only. These checks support observer behavior and compilation, not physical controller success.

The prepared 88ab read-only adjudication and one-attempt hardware packet correctly require a new exact SHA/UF2 binding and defer all device action. Their interpretation must retain these limits: YELLOW may be UNPLUGGED processing, BLUE counts at least two DCD reset emissions during the first active invocation rather than a proven perpetual storm, and GREEN only proves that first invocation returned. No later-task stall is visible in the settled pair without working serial telemetry. Hardware PASS, root cause, and Nunchuk testing remain unclaimed.
