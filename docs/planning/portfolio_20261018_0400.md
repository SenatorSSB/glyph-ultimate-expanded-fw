## Direct owner chapter scope

Source: direct project-owner `/goal` request in the current chapter daemon on
2026-10-18 (thread `01a14c77-92f5-7940-9dde-eb1926310ffe`). The owner directs
the first production vertical slice of Profile-Defined Controller Function
Bindings, with X1 as the initial function. Its required boundary is:

```text
physical Glyph input
-> profile-defined binding / condition
-> firmware-defined bounded controller-function class
-> profile-defined bounded parameters / priority
-> virtual controller output
```

The request supersedes the roadmap's prior sequencing-only `FUTURE_ARCHITECTURE`
status for this named chapter. It does not supersede the hardware gate, grant
device write/flashing authority, authorize game semantics, macros/turbo/timing,
or permit a ProfileStore redesign. X2, Y1, Y2, Tilt, RT2, factory recovery,
Nunchuk, Senscope, and unrelated deferred evidence are excluded.

## Current facts and source authority

- `docs/ROADMAP.md` documents the intended ownership boundary: firmware owns a
  finite function vocabulary, validation, deterministic ordering, and conflict
  resolution; profiles own instances, bindings, conditions, and bounded
  parameters. It keeps game semantics Senscope-owned and rules out scripting,
  macros, turbo, timing, and arbitrary expressions.
- `src/modes/Ultimate.cpp` currently assigns X1 from `inputs.lt5` in
  `ResolveRoleState`, counts it in the existing modifier conflict algorithm,
  resolves sole X1 to `RuntimeTableId::X1` or `RuntimeTableId::MX1`, and then
  lets the V2/V3 profile table-rule evaluator select by unique numeric priority.
- `UltimateProfileEvaluator::RouteLogicalInputs` already maps physical inputs
  to logical slots. The current residual coupling is that the routed LT5 slot
  intrinsically means X1. A V3 table rule must be accounted for; changing only
  `RoleState::x1_active` would not be an effective binding slice.
- `ProfileStore` persists, validates, and activates a bounded `UltimateProfile`
  in separate candidate and active storage. This proposal reuses that lifecycle;
  it does not introduce another store, publication path, device-write flow, or
  hot reload.
- Current generated X1 coordinates are the nine entries in
  `src/modes/runtime_config/generated_source_owned/GeneratedRuntimeConfigBaseline.current.hpp`.
  The historical `current_x1_regression_subset` fixture describes an older
  offset-41 table and is explicitly excluded as current correspondence proof.

## Candidate: GP-BIND-001

**Title:** Profile-defined X1 stick-table-modifier binding vertical slice

**Planning disposition:** `CURATION_READY`.

**Objective:** Add one persisted, typed, bounded `STICK_TABLE_MODIFIER`
function-binding representation to a new Ultimate-profile schema version and
make its one X1 instance control the already-accepted X1/MX1 selection path.
The baseline binding must reproduce the current profile's physical-to-routed-LT5
mapping, so its observable controller output remains exactly unchanged.

**Proposed bounded design:**

- Define a firmware-owned closed function class for stick-table modifiers and
  reject unspecified/unknown classes, duplicate instance IDs, unknown tokens,
  invalid table IDs, ambiguous priority, and unsupported shapes.
- Define a profile-owned function instance with a bounded physical-input
  condition, a bounded conflict priority, and base/mode table parameters. The
  first profile version admits exactly one X1 instance in the existing
  left-stick-table conflict domain; later migrations may add instances using the
  same representation, not new X1 fields.
- Resolve the function condition from the once-preprocessed physical snapshot,
  before logical-slot routing. This is the requested physical-binding domain;
  `RouteLogicalInputs` remains available for all unmigrated legacy functions.
- Preserve the legacy X1 conflict result by supplying the binding's active
  result to the same modifier-count/precedence calculation. Preserve the
  existing V2/V3 `SelectTable` deterministic unique-priority rule path rather
  than allowing array order or a second evaluator to decide an output.
- Preserve v1/v2/v3 profiles byte-for-byte and behaviorally through their
  legacy path. New V4 profiles must contain a complete valid binding declaration;
  omitted/malformed bindings reject before ProfileStore publication. No stored
  record is migrated in place during this slice.

This is a source-grounded engineering choice under the direct owner's requested
physical-binding architecture. It adds no game vocabulary: X1 is a firmware
controller-function instance whose output is existing bounded table selection,
not a game action.

**Hardware risk:** H3. The profile wire shape, ProfileStore admission and active
input/selector path are persistence and critical-dispatch adjacent. H3 is
conservative; no merge is eligible before exact candidate/artifact human PASS.

**Closed scope:** `schema/haybox/config.proto` and generated outputs/options;
Ultimate profile config/evaluator and semantic validator; `Ultimate.cpp` X1
activation/selector seam; focused fixtures/checkers; exact candidate,
source/build/resource/review/custody/hardware records; narrowly required
current-state/roadmap/queue/user-direction updates.

**Excluded scope:** every other function family; Stage A/B/C redesign; dynamic
functions; arbitrary profile code; macros/turbo/timing; game semantics;
ProfileStore storage/recovery/transaction redesign; runtime-loaded config
activation; device/config/protobuf writes; flashing automation; factory
recovery; RT2; Senscope; Nunchuk.

**Required proof before a READY disposition:**

1. Exhaustive source inventory/correspondence for current X1 activation,
   conflict selection, V2/V3 table-rule override, remap/SOCD input order and
   current generated X1/MX1 coordinates.
2. Schema/wire, fixed-capacity/RAM, validator and ProfileStore admission proof
   for V4; v1/v2/v3 byte/behavior compatibility and rejected-shape negatives.
3. A finite X1 matrix covering the baseline binding, alternative physical
   binding, release/hold, Mode/MX1, neutral/directions, simultaneous modifiers,
   overrides, reordered declarations, nonidentity routing, and profile A/B/A
   selection isolation.
4. Directly affected Stage A/B/C, profile semantic, ProfileStore selection,

   Mk6 build/resource review.
5. Fresh source-authority/safety and post-implementation independent reviews;

   and a source-free, exact-candidate hardware protocol before integration.

**Stop conditions:** any unsupported physical-input domain, unexpected V3
correspondence contradiction, V4 wire/capacity failure, active ProfileStore
publication/storage change beyond this representation, a required function
class outside stick-table modifier, a Tier-1 or affected Tier-2 failure, or
the hardware gate. Tier-3 framework debt remains recorded, not relabeled PASS.

## Rejected alternatives

- Reusing routed LT5 as the new binding input: retains the intrinsic logical-slot
  meaning that the chapter is meant to remove.
- Changing only `RoleState::x1_active`: V2/V3 table rules subsequently select a
  table, so it does not establish an end-to-end binding abstraction.
- Using the old offset-41 X1 fixture as a baseline: it does not match the live
  generated source table.
- Generalizing all modifier families now: conflicts with the deliberately
  narrow X1 proof slice and enlarges controller behavior without proof.
- Introducing a new ProfileStore, runtime publication path, device protocol or
  dynamic evaluator: outside the owner scope and implementation boundary.
