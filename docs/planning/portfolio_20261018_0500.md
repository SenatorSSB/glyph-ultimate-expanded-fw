## GP-BIND-001

The direct project-owner goal of 2026-10-18 in thread
`01a14c77-92f5-7940-9dde-eb1926310ffe` authorizes this X1 first slice and
excludes other families, Stage A/B/C redesign, ProfileStore redesign, game
semantics, scripts/macros/turbo/timing, device writes, flashing, RT2, recovery,
Senscope and Nunchuk.

V4 adds a fixed-capacity generic function-binding record. Firmware admits only
`STICK_TABLE_MODIFIER` / `X1` now and rejects unspecified, unknown, duplicate,
missing and extra records. The record is generic for later separately authorized
function instances. Its activation condition is physical-button tokens from the
once-remapped/SOCD-preprocessed, pre-profile-routing `InputState.buttons`
snapshot. It has bounded base/mode table IDs and distinct nonzero base/mode
priorities in the existing 1..255 table-selection uniqueness domain.

V4 removes only old role 2 (X1), without renumbering other roles. It derives the
closed function token `F_X1` before evaluating remaining roles. Ordinary V4 rules
may reference that token; binding conditions may not reference roles/functions;
no old role-2 token may remain. Existing rule conditions retain their bounded
vocabulary, with V4 ordinary rules additionally allowing the closed function
token namespace under validation.

One selector evaluates ordinary rules and synthesized X1 candidates in the same
lowest-unique-priority domain. Let E mean any of roles 3,4,5,14,15,19,20,21
(the V3 X1 competitor tokens 67,68,69,78,79,83,84,85):

```text
MX1 = F_X1 && role1(mode) && !E -> mode table at mode priority
X1  = F_X1 && !role1(mode) && !E -> base table at base priority
```

The V4 baseline derives its physical token from V3 routing slot 37 (LT5), uses
mode/base tables 4/2 and priorities 10/11, replaces all V3 positive role-2
references with `F_X1`, and all negative role-2 references with `!F_X1`. The
deleted V3 X1 rules' competitor exclusions remain attached to synthesized
candidates. Thus LT5+LT4 and Mode+LT5+LT4 remain Default conflicts, not X1.

V4 retains V3's Stage-C shape (32 routing slots, 12 effects, one logical routing
pass, phase ordering and validation). V1/V2/V3 behavior remains unchanged.
ProfileStore may add V4 payload admission only; no record/transaction/recovery
change, no limit increase beyond 4096-byte profile/4128-byte record, and no
candidate-to-active publication change are permitted.
