## Engineering resolution

This contract resolves the independent Curator's concrete finding that V2/V3
`SelectTable` ignores its legacy selector argument and chooses a profile rule by
unique numeric priority. The new X1 binding must therefore participate in that
same selector, including every positive and negative X1 dependency; it must not
be an inert side channel.

The binding input domain is the `InputState.buttons` snapshot after the existing
remap/SOCD preprocessing and before Ultimate-profile logical routing. It is a
physical Glyph-input domain for this firmware architecture, not an unprocessed
electrical sample and not a routed logical slot. This preserves the established
controller input pipeline while removing LT5's intrinsic X1 meaning in V4.

## Candidate: GP-BIND-001

**Title:** Profile-defined X1 stick-table-modifier binding vertical slice

**Planning disposition:** `CURATION_READY`.

**Closed V4 representation:**

1. `UltimateProfile` V4 adds a fixed-capacity list of typed function bindings.
   Firmware defines the only admitted class in this slice,
   `STICK_TABLE_MODIFIER`, and its only admitted instance ID, `X1`. Unknown,
   unspecified, duplicate, omitted, out-of-range, or extra instances reject.
   This is a generic record shape, not an X1-only field; later function families
   may add separately authorized finite instance IDs/classes using the same
   representation.
2. The X1 instance owns an all/any/none condition over physical tokens only,
   a base-table ID with its unique priority, and a mode-table ID with its unique
   priority. All IDs are bounded existing runtime-table IDs. The two priorities
   must be nonzero, distinct, and share the existing table-rule priority domain.
   No persisted-array order is executable.
3. The evaluator first resolves V4 function-binding activation from the once
   preprocessed pre-routing input snapshot. It exposes the active instance only
   through a closed function-token range, separate from physical and role
   tokens. Function-binding conditions may use physical tokens only, preventing
   role/function cycles and a second expression language.
4. The V4 selector evaluates existing roles and table rules plus the active
   binding's two synthesized candidates in one lowest-unique-priority selection.
   The mode candidate is eligible only when the existing profile mode role is
   active; its base candidate is otherwise eligible. These candidates use the
   binding's declared base/mode table IDs and priorities. The existing fixed
   modifier conflict behavior is preserved by V4 table rules: every legacy
   positive X1 reference is replaced by the X1 function token, and every legacy
   negative X1 reference is replaced by its negation. The old X1 role and its
   two source rules are absent from V4. No V4 evaluator consults routed LT5 to
   activate X1.
5. The V4 baseline is mechanically derived from the accepted V3 correspondence:
   its X1 binding condition equals the physical input token currently mapped to
   the V3 LT5 routing slot; its base/mode table IDs and priorities equal V3's
   X1/MX1 rule rows (2/4 at 11/10); and all dependent table-rule conditions
   replace role token 66 with the X1 function token. This preserves identity and
   nonidentity routing behavior while removing the logical-slot dependency.
6. V1/V2/V3 profiles retain their existing evaluator and wire behavior. V4 is
   additive only: no in-place ProfileStore migration, record-format redesign,
   RuntimeConfigView change, hot reload, device write, or transaction change.
   ProfileStore continues to validate/decode candidate storage and copy only an
   accepted profile into dedicated active storage.

This defines profile-owned binding/condition/table parameters and priority while
firmware owns the closed class/instance/token vocabulary, syntax validation,
evaluation order, and conflict semantics. It expresses no Smash/game action,
macro, timing, script, turbo, or arbitrary execution.

**Behavioral claim:** A valid V4 baseline profile produces exactly the accepted
V3 X1/MX1 controller output for every relevant processed input, including
nonidentity routing and all X1 conflict cases, while a V4 profile can bind that
same finite X1 table-modifier instance to a different physical input without
giving that input intrinsic firmware meaning.

**Hardware risk and classification:** H3 /
`FIRMWARE_SOURCE_ACTIVE_BEHAVIOR`: persisted profile schema, admission and the
active input/selector path change. No source integration is eligible before
exact candidate build, custody, source-free HEP PASS and fresh integration
review.

**Required validation contract:**

- Enumerate and compare all V3 X1 positive/negative role/rule dependencies
  against the V4 function-token rewrite, including the V3 rules at priorities
  10/11 and all competing modifier exclusions.
- Prove the V4 baseline over the exhaustive existing selector/direction matrix,
  remap/SOCD sequence, neutral/direction/Mode/MX1 cases, simultaneous modifiers
  and overrides; include nonidentity routing and declaration reordering.
- Add a bounded alternative-physical-input V4 case and prove it changes only
  X1 activation, never an unrelated logical slot or function.
- Reject unknown class/instance/token, duplicated binding/function token,
  mode/table/priority conflicts, physical condition containing role/function
  tokens, missing replacement dependencies, excess bindings and V4 omissions.
- Preserve V1/V2/V3 fixtures and ProfileStore candidate rejection/active-state
  preservation. Measure generated structure/descriptor/encoded sizes against
  current Nanopb and the 4096-byte profile / 4128-byte record bounds.
- Run both enum ABIs; actual profile semantic, Stage A/B/C, ProfileStore
  selection/recovery/config-persistence checks; canonical `pio run -e
  glyph_mk6`; resource review; source correspondence; fresh independent review;
  exact artifact custody and HEP protocol.

**Excluded scope:** X2/Y1/Y2/Tilt and every other family; generalized multiple
function instances; Stage A/B/C redesign; ProfileStore storage/recovery or
protocol redesign; runtime-config publication; device/config/protobuf writes;
flashing; RT2; factory recovery; Senscope; game semantics; Nunchuk; macros,

**Source evidence:** `src/core/ControllerMode.cpp` establishes the remap/SOCD
