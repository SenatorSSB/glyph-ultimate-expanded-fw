## GP-BIND-001 — Profile-defined X1 stick-table-modifier vertical slice

The direct owner goal in thread `01a14c77-92f5-7940-9dde-eb1926310ffe` on
2026-10-18 authorizes this first production slice. It excludes other function
families, Stage A/B/C redesign, ProfileStore redesign, game semantics, scripts,
macros, turbo, timing, device/config writes, flashing, RT2, factory recovery,
Senscope and Nunchuk.

V4 adds a fixed-capacity generic binding record. Firmware admits exactly one
closed `STICK_TABLE_MODIFIER` / `X1` record; unknown, unspecified, duplicate,
missing or extra records reject. Its activation condition uses only physical
tokens from the existing remap/SOCD-processed, pre-profile-routing
`InputState.buttons` snapshot. The profile supplies bounded base/mode table IDs
and distinct nonzero base/mode priorities in the existing shared 1..255 unique
table-selection domain.

V4 removes only legacy role 2/X1 without renumbering remaining roles. It derives
closed function token `F_X1` before evaluating remaining roles; ordinary V4
rules may reference that token, but binding conditions cannot reference roles
or functions. Every former positive/negative role-2 reference becomes
`F_X1`/`!F_X1`; residual role-2 tokens reject.

The existing selector evaluates ordinary rules and two synthesized X1 candidates
together by lowest unique priority. With E = roles 3,4,5,14,15,19,20,21:

```text
MX1 = F_X1 && role1(mode) && !E -> mode table at mode priority
X1  = F_X1 && !role1(mode) && !E -> base table at base priority
```

The baseline derives its physical input from current V3 routing slot 37/LT5,
uses tables 4/2 and priorities 10/11, and keeps the deleted V3 X1 rules'
competitor exclusions on the synthesized candidates. Thus LT5+LT4 and
Mode+LT5+LT4 retain accepted Default conflict results. Alternative physical
bindings change only this finite X1 instance; no physical/logical slot carries
intrinsic X1 meaning in V4.

V4 retains V3 Stage-C: 32 routing slots, 12 effects, one routing pass, phase
ordering and validation. V1/V2/V3 stay behaviorally unchanged. ProfileStore may
add V4 payload admission only; record format, transactions, recovery,
4096-byte-profile/4128-byte-record limits and candidate-to-active copying are
fixed.
